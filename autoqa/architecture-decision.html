Why a scheduled container wins

WINNERScheduled container job

A fresh container per run deletes a whole class of failure
  • No time cap. Unlike Lambda, a Fargate task or Container Apps Job runs as long as it needs — a 133-minute run is fine.
  • Kills the process-leak class outright. This repo documents orphaned daemons piling up on a long-lived machine — 13 at PPID=1 after one run, 19 agent-browser + 15 Chrome overnight, 8.4 M swapouts degrading CDP. A container that exits takes all of it with it. Every run starts genuinely clean.
  • Makes the recycle() collateral-damage bug impossible. That broad-kill fallback has fired for real 4+ times, killing other sessions' browsers. One session per container means there is nothing else to kill.
  • You pay for ~60 hours, not 730. 2 vCPU / 8 GB at ~2 runs/day ≈ $6–9/mo against $30–90 for a box idle 95% of the time.
  • Nothing to patch. No OS upkeep, no drifting host.

Azure equivalent: Container Apps Jobs, which takes both cron and event triggers — so it also covers stage 2 if you build that yourself.

✓EC2 — the honest runner-up

Simpler state, easier debugging, more money

Two real advantages: EBS is simpler than an EFS mount for the 128 MB of learned state, and you can SSH in while a daemon is wedged — which matters on a project whose hardest bugs were found by live instrumentation rather than log-reading.

The cost gap is ~$25–80/mo, small in absolute terms. Pick this if operational familiarity is worth more to you than the clean-slate guarantee.

Burstable is fine here now. The earlier warning about T3 credit drain assumed back-to-back cycling. At ~2 runs/day with 22 idle hours, credits replenish faster than they drain — t3.medium at ~$30/mo is legitimate.

✓Run test --flow, never run

The command matters as much as the host

The requirement is certain selected flows, and test --flow <id> is the only command that expresses it. run tests every approved flow.

Worse: CLAUDE.md warns run skips exploration only if the sitemap has pages and approved flows. On a fresh container with a failed EFS mount it silently triggers a full exploration — the expensive cold-start path, re-proposing flows nobody approved. explore must be human-gated and unreachable by the schedule.

Why not the others

✕AWS Lambda

Disqualified on one measured fact

The 15-minute ceiling is a maximum, not a tunable. 51 of 157 measured runs exceed it, and every deep run does — they'd be killed mid-flow with no verdict recorded.

Secondary: no persistent disk (state would need EFS bolted on), a 10 GB /tmp ceiling for screenshots, and packaging Chromium into a layer is fiddly. Still useful as a trigger — EventBridge → tiny Lambda → start the real job.

✕RunPod

Paying for silicon you never touch

A GPU cloud — A100s and H100s by the hour, built for training and serving models where the GPU is the point. autoqa needs zero GPU: the intelligence is a remote Anthropic API call, not a local model.

On the CPU-pod side it's a bare container host with thin cron, secrets, IAM and monitoring tooling — strictly worse than options 1–4 at a higher price.

✕Replicas re-check

Right VM, wrong trigger model — and it wins stage 2

It is a real VM with Docker, so autoqa could technically execute there — the closest of the four non-compute options. But the model is task-in → PR-out, not cron-in → report-out.

  • No scheduler. Nothing fires work every N hours; a ticket or message does.
  • Sleeps idle, deleted after 7 days. Precisely the wrong durability guarantee for state you must never lose.
  • Per runtime-minute billing. 24/7 almost certainly exceeds a $70 dedicated VM.

Every one of those flips to an advantage in stage 2. Keep it — just for the other half.

✕Cognition · Devin

Wrong category, not wrong quality

Devin is an AI software engineer that works in its own cloud sandbox: you hand it a ticket, it writes code and opens PRs. Priced in agent-style compute units.

Cognition doesn't sell scheduled compute. You already have an autonomous agent — autoqa — and you need somewhere to host it. Paying agent-grade rates to babysit an npm run qa loop is expensive and architecturally backwards. It belongs in stage 2.

✕VeilStream

Not a compute platform at all

A lightweight proxy in front of a PostgreSQL database that masks or hides sensitive fields per-user, so teams work against production-like data without touching real PII. It also spins ephemeral PR-preview environments from a docker-compose.yml.

It cannot host a scheduled job. But it is adjacent to a real problem you have — see the closing note on those 4.1 GB of screenshots.

!GitHub Actions

Fine to prototype, too weak to live on

The 6-hour job cap is ample and the ergonomics are excellent. The problem is state: 128 MB of learned statements would live in cache/artifacts, which is a best-effort store, not a durable one — and losing it means re-teaching the agent.

Running back-to-back 45-minute jobs also burns Actions minutes at a rate that stops being cheap.

Why Replicas wins here after losing badly for stage 1

Every trait that disqualified it as autoqa's host is either irrelevant or an outright advantage for a fix agent. That is the clearest signal that these are genuinely two different problems.

WINNERReplicas

It is, almost literally, this product

A YC-backed cloud coding-agent platform. You assign a task from GitHub, Slack, Linear or a dashboard; it spawns Claude Code (or Codex / Cursor / Opencode) in an isolated VM holding your repo and a real dev environment — Docker, npm, databases.

The agent verifies its own work locally, opens a PR, then reads CI failures and code-review comments and iterates. That is stage 2, described by its own marketing.

  • Feedback loop is built in — it fixes its own CI failures rather than handing you a red PR.
  • Preview URLs from configured environments, so a reviewer can see the fix running.
  • No code stored in their databases; it stays in your connected repo and isn't used for training.

!Two things to check before committing

Both are dealbreakers if they apply to you

1. Jira is not a listed integration. Documented triggers are GitHub, Slack, Linear and a dashboard. If Jira is fixed for you, either bridge Jira → GitHub issue, drive it via its API, or drop to option 4 and build stage 2 yourself.

2. It runs on its own cloud, not Azure. If Claude and the compute must both sit inside Azure for policy reasons, Replicas is out and it's Azure Container Apps Jobs + Claude Agent SDK.

That second point is the real fork in the design — see the constraint card below.

Why not the others

✓Cognition · Devin — #2

Same category, less flexibility

Genuinely purpose-built for this and more mature on the enterprise side. Two reasons it lands second: it's one proprietary agent where Replicas lets you pick Claude Code, Codex, Cursor or Opencode; and agent-tier pricing is higher than per-runtime-minute for the same work.

If you specifically want a Claude fix, Replicas naming Claude Code as a first-class option is a direct match rather than an approximation.

✓GitHub Actions — #3, and the best pilot

Near-zero new infrastructure

Loses stage 1 on state, wins here because stage 2 has no state. It's already attached to the repo with secrets configured and native PR creation, and the 6-hour cap is far beyond what a fix needs.

Start here. A workflow triggered by an issue label, running the Claude Agent SDK, on one narrow bug class — that's a low-risk way to prove the loop before paying for a platform.

✓Container Apps Jobs / Fargate — #4

The answer if Azure is mandatory

Purpose-built for per-task ephemeral containers with both cron and event triggers — exactly the shape of "a ticket arrived, go fix it." You supply the container; the platform supplies the isolation, queueing and cleanup.

Pair it with the Claude Agent SDK (Claude Code as a library: built-in read/write/edit/bash/grep plus the agent loop) and the AnthropicFoundry client if billing must route through Azure.

!EC2 / VPS — #6

It works; you just build what others give free

Nothing stops you running the fix agent on the same box as autoqa. But you'd hand-build the job queue, per-ticket isolation, concurrency limits and workspace cleanup that options 1–5 include.

Worse, co-locating means a runaway fix agent can starve the finder — and a wedged Chromium can take the fixer down with it. Keep the two stages on separate compute.

!AWS Lambda — #7

Much better here than stage 1, still poor

Stage 2 is short, so the 15-minute cap is no longer automatically fatal — but a coding agent that clones a repo, reproduces a bug, fixes it and runs the test suite can plausibly exceed it, and you'd lose the work with no partial result.

Running the product's own test suite inside a Lambda sandbox is also awkward. Options 3–5 cost the same order of money with none of the ceiling.

✕RunPod & VeilStream

Unchanged from stage 1

RunPod: still zero GPU needed. A coding agent is I/O and API-bound; renting an H100 to run git clone and npm test is pure waste.

VeilStream: still a Postgres PII-masking proxy. It doesn't execute your code and can't open a pull request.

03

The stack, assembled — find → ticket → fix → re-test

Two independently-deployed stages with a ticket queue between them. The loop closes because stage 1's next cycle is the independent verification of stage 2's PR — which only means something if a human merged it first.

Stage 01 · scheduled

autoqa on Fargate

  1. EventBridge fires the task ~2×/day
  2. test --flow <id> on selected flows, headless
  3. Verifies via DOM + console + network + vision
  4. Files a structured Jira issue, posts to Slack
  5. State on EFS, artifacts to S3 with 30-day lifecycle
→Jira
ticket
Stage 02 · per-ticket

Claude fix on Replicas

  1. Webhook on label autoqa
  2. Isolated VM, repo + dev env ready
  3. Claude Code reproduces and fixes
  4. Verifies locally, opens a PR
  5. Human reviews and merges — never auto-merge
✕Blocker — fix this before anything else ships

An unanswered prompt stalls 300 s then takes a default. For a console error that default is noise (statements.ts:210) — scoped global, and fed into allowedConsoleErrorPatterns, which suppresses that error site-wide, permanently.

The codebase already knows this is dangerous: the LLM auto-noise pass deliberately excludes console errors for exactly this reason, in its own comment. The timeout default bypasses that safety property at the human layer. Failed to fetch JSON from S3 is a console error — so an unattended loop would teach itself to stop reporting the bug the Slack reporter exists to report.

Also: approve-flows defaults to all when unanswered — auto-approving every LLM-proposed flow with zero review. This project's history includes an auto-proposed flow that drove a real browser to a live third-party Teachable checkout with an order ID.

✕Duplicate tickets — fix before wiring Jira

Slack dedupe groups errors within one run; there is no cross-run fingerprint store. So a 24/7 loop files a new Jira ticket every cycle for the same standing bug — and each one spawns a fix agent burning tokens re-fixing what's already in an open PR.

✕The agent must not silence the test

Given a failing check, an agent can satisfy it by fixing the product or by weakening the assertion. Scope stage 2 to the product repo only — never autoqa's .autoqa-state, statements KB, or verification.ts. A bug that vanishes because the oracle got edited is worse than the bug.

!Backend bugs need the backend repo

The S3 failure returns HTML where JSON is expected — a server-side fault. An agent can only fix that with access to the service serving the endpoint. Scope the pilot to front-end and harness findings.

!Sequence it — don't build both at once

Ship stage 1 with the console default fixed → add cross-run dedupe → add structured Jira issues → then stage 2 on one narrow bug class. A fix agent fed by an untrustworthy finder just automates the production of bad PRs.

!Where VeilStream is genuinely relevant

Not as a host — but you're running an autonomous agent that fills forms, uploads files and screenshots pages. Those 4.1 GB of screenshots and network logs can capture real user data, and CLAUDE.md already records live JWTs found in captured network JSON. If xp/beta are ever seeded from production-like data, a PII-masking proxy in front of the test database is the right category of tool. Separate decision from where the runner lives.
